1.2 基盤モデルの選定と構成

どのモデルを使うかを、コードの外に出す話です。切り替えも、地域の制約も、モデルの寿命も、設定として扱えば再デプロイが要らなくなります。

社用車の管理に似ています。車種は業務に合わせて入れ替えられるようにし、走ってよい地域は規則で決め、車検が切れる前に手を打つ。どれも車に乗る人が個別に判断することではなく、台帳で管理する事柄です。

どこで間違えるのか

モデル ID をコードに書く。 規制やコストで使い分けたい、A/B で比べたい、そのたびに再デプロイが必要になります。設定として外に出せば、配布と切り戻しも仕組みに乗せられます。

クロスリージョン推論を速くなる仕組みだと思う。 これは容量と耐障害性を得る手段であり、同時に地理の境界を保つ手段でもあります。レイテンシを縮める道具ではありません。

モデルの寿命を気にしない。 Legacy や提供終了予定と表示されているモデル ID を埋めたままにすると、ある日突然動かなくなります。後継版の評価と段階的な移行を、日常の運用として組み込みます。

こう言われたら、これを選ぶ

問題文の手がかり選ぶもの理由
コード変更なしで切り替え AppConfig の動的設定 再デプロイが要らない
段階配布と自動切り戻し 検証・配布戦略・アラーム連動 事故を小さく抑える
地理の境界を保って分散 地理プレフィックス付きプロファイル 域内だけで散らせる
制約なく広域の容量を使う グローバルなプロファイル 最も広く取れる
提供終了の前に移行したい モデルのライフサイクル情報 事前に気づける
承認済みの版だけ本番へ Model Registry と段階昇格 版と承認を管理できる

覚えておく数字と制限

  • 地理プレフィックス付きの推論プロファイルを許可するには、プロファイル自体、呼び出し元リージョンの対象モデル、そしてすべての宛先リージョンの対象モデルに API 権限が要る。 あわせて SCP が宛先リージョンを拒否していないことも確認する。
  • データレジデンシーの制約がなく、広域のオンデマンド容量を使いたいならグローバルなプロファイル。制約があるなら地理単位のプロファイルを選ぶ。
  • モデルのライフサイクル情報を監視し、提供終了の前に後継版を評価してカナリアや A/B で段階導入する。本番の設定は明示的に更新する。
  • 取り込んだモデルが Converse に対応していれば、オンデマンドのスループットで InvokeModel 系と Converse 系の両方から呼べる。既存のチャット画面にも接続しやすい。

2.2 との違いは、こちらが「どのモデルを選び、どう切り替えるか」で、2.2 が「選んだモデルをどう配置するか」です。同じ推論プロファイルでも、選定の文脈で出るか配置の文脈で出るかで、問われている点が変わります。

紛らわしいものの対比

問題文に「コードを変更せずに」「再デプロイなしで」が出たら設定の外出しです。さらに「安全なロールアウト」「検証」「ロールバック」が並んでいたら、単なる設定保存ではなく、配布戦略とアラーム連動まで持つ選択肢を選びます。
