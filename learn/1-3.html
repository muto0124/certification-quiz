1.3 データ検証・処理パイプライン

モデルに渡す前の工程を扱います。ここでの取りこぼしや汚れは、後段の検索でも生成でも取り返せません。

料理の下ごしらえです。魚は骨を抜き、乾物は戻し、野菜は皮をむく。素材が違えば下処理も違いますが、済ませたあとは同じまな板の上で扱えるように揃えます。ここを飛ばすと、どれだけ腕のいい料理人でも仕上がりません。

どこで間違えるのか

生のデータをそのままモデルへ渡す。 スキャンされた PDF も、通話録音も、点検写真も、まずテキストと構造化データにしてからでないと扱えません。媒体に合った抽出サービスを選ぶところが最初の分岐です。

品質の検証を埋め込みの後ろに置く。 契約番号の欠落や日付形式の乱れは、ベクトル化されてしまえば索引の中に残り続けます。品質ゲートは埋め込みの前に置き、通らなかったレコードは隔離します。

媒体ごとにバラバラのスキーマで保存する。 PDF から取った結果と音声から取った結果を別々の形で持つと、横断した検索も引用もできません。抽出後に共通の text と metadata へ正規化してから取り込みます。

こう言われたら、これを選ぶ

問題文の手がかり選ぶもの理由
スキャン PDF から文字を取る Amazon Textract 表や帳票の構造ごと読む
通話録音から文字を取る Amazon Transcribe 音声に合う抽出を使う
画像・音声・動画をまとめて Bedrock Data Automation マネージドに寄せられる
埋め込み前に品質を守る Glue Data Quality 失敗レコードを隔離できる
数十 GB を時間内に処理 Step Functions と分散処理 単一の関数では届かない
PII を落としてから投入 Comprehend や Guardrails 索引に載る前に消す
S3 への到着で動かしたい EventBridge から起動 ポーリングが要らない

覚えておく数字と制限

  • 品質ゲートは埋め込みの前。 後ろに置くと、汚れたデータから作ったベクトルが索引に残る。Glue Data Quality で検証し、通らなかったレコードは隔離して、品質指標を CloudWatch で追う。
  • 媒体が違っても、抽出したあとは 共通スキーマ（text と metadata）に正規化してから Knowledge Base に取り込む。引用と検索を横断させるための前提。
  • Bedrock Data Automation のジョブ状態は EventBridge のイベントで受け取れる。ポーリングは不要。
  • 個別サービスとまとめ役の使い分け。媒体ごとに細かく制御したいなら Textract や Transcribe、多様な媒体をまとめて任せたいなら Bedrock Data Automation。

大量データを時間内に処理する条件が出たら、単一の Lambda で回す選択肢は落ちます。Step Functions で分散処理を束ね、PII 除去と埋め込み生成まで一続きにする組み立てが基本形です。

紛らわしいものの対比

問題文に「検索品質が安定しない」「取り込んだデータに欠落がある」が出たら、前処理の順序を疑います。選択肢のうち、検証を埋め込みの後ろに置いているものは落とせます。
