2.1 エージェント型 AI とツール連携

エージェントは4つの部品でできています。記憶、道具、境界、人の介在。どれをマネージドに任せ、どれを自分で持つかで構成が決まります。

新人に仕事を任せるのと同じです。何を覚えておいてもらうか、どの道具を使ってよいか、どこから先は勝手に進めないか、誰が最終確認をするか。この4つを決めずに「よろしく」とだけ言うと、事故が起きます。

どこで間違えるのか

全部を1つのエージェントに詰め込む。 領域が増えるほど指示と道具の管理が複雑になります。専門ごとにエージェントを分け、入口となる1体が内容に応じて委任する構成のほうが、既存の作り込みも活きます。

権限をモデルへの指示で守ろうとする。 「送金は 10 万円まで」と system prompt に書いても、それは指示であって制約ではありません。実行前に決定的に判定する仕組みが要ります。

長い処理を同期で待たせる。 複数のソースを集めて解析するような仕事を、受付の応答と一緒に返そうとすると、接続がタイムアウトします。受付だけ返し、処理は非同期で続けます。

こう言われたら、これを選ぶ

問題文の手がかり選ぶもの理由
専門エージェントが既にある 入口役と委任先の構成 既存を活かせる
会話の中で属性を保つ セッション属性 同一会話で共有する
会話をまたぐ好みや履歴 長期の記憶 セッションを越える
既存 API を道具にしたい Gateway で MCP 互換に 作り直さずに済む
軽い状態なしの道具 Lambda に置く 起動が軽い
依存が多く重い道具 ECS に置く 実行環境を持てる
実行前に確実に止めたい 事前判定のポリシー 指示では守れない
人の承認を挟む トークン待ちのワークフロー 実行を止められる

覚えておく数字と制限

  • アクショングループの Lambda を呼ばせるには、Lambda 側のリソースベースポリシーで bedrock.amazonaws.com に lambda:InvokeFunction を許可する。 エージェントのサービスロールに権限を付けるだけでは呼び出せない。
  • 必須の入力は、関数定義か OpenAPI スキーマで required として宣言する。欠けていればエージェントが利用者へ追加で質問するので、同じ条件をアプリ側に重複実装しなくて済む。
  • Converse の toolChoice は any と auto で意味が違う。前者はどれか必ず使わせる、後者は使うかどうかもモデルに委ねる。
  • 記憶は2種類。直近のやり取りは短期、製品シリーズや担当地域や回答形式の好みのようにセッションをまたぐ属性は長期に置く。
  • 外部サイトの操作と、コードを走らせる処理は、それぞれ分離された別の環境で行う。同じ仕組みに押し込まない。
  • Amazon Bedrock Agents は「Agents Classic」に改称され、新規顧客の受付を終了している。 既存利用者はそのまま使えるが、これから作るなら後継の AgentCore を見る。問題集にアクショングループと AgentCore の両方が出てくるのはこの過渡期のため。

紛らわしいものの対比

問題文に「専門ごとのエージェントが既に本番で動いている」「それぞれにアクショングループとナレッジベースがある」と書かれていたら、機能を1体へ移し替える選択肢は落とせます。既存を活かしたまま入口を作るのが狙いです。
