2.2 モデルのデプロイ戦略

同じモデルでも、呼び出し方をどれにするかで、料金の形と「混んでいるときに使えるか」が変わります。それを選び分けるのがデプロイ戦略です。

タクシーで考えると分かりやすくなります。オンデマンドは流しのタクシーで、乗った分だけ払えばよい代わりに、雨の日は捕まりません。プロビジョンドスループットは専用車の月極契約で、毎月同じ額を払うかわりに、いつでも必ず乗れます。SageMaker AI エンドポイントは車を自分で買うようなもので、好きに改造できますが車検も洗車も自分の仕事です。

どこで間違えるのか

「プロビジョンドにすると速くなる」と思ってしまう。 買っているのは容量であって速度ではありません。1 回の応答が速くなるわけではなく、混雑時にスロットリングされずに済む、という保証を買っています。レイテンシを縮めたいなら、モデルを小さくする、プロンプトを短くする、ストリーミングで返し始める、といった別の手を打つことになります。

容量を買ったのに使えていない。 プロビジョンドスループットを購入しても、コード側の modelId が基盤モデル ID のままなら、リクエストは従量課金の経路に流れます。買った容量を使うには modelId をプロビジョンドモデルの ARN に差し替える必要があります。

プロビジョンドなら何でもできると思ってしまう。 容量を確保すると制約がなくなる気がしますが、逆に使えなくなる機能があります。代表がバッチ推論です。

こう言われたら、これを選ぶ

問題文の手がかり選ぶもの理由
トラフィックが読めない、試作段階 オンデマンド（基盤モデル ID か推論プロファイル） 事前契約が要らず、使った分だけの課金で済む
一定量の負荷が常時ある、スロットリングを避けたい プロビジョンドスループット モデルユニットを購入して容量を確保できる
ファインチューニング済みモデルを本番で使う（Amazon Nova 以外） プロビジョンドスループット 専用の Provisioned Model ARN を作らないと呼び出せない
夜間に大量処理、応答は即時でなくてよい バッチ推論（オンデマンド） S3 の入出力で非同期に処理できる。プロビジョンドとは併用できない
独自コンテナ、GPU、自前モデルが必要 SageMaker AI エンドポイント Bedrock の枠外。自由度と引き換えに運用を持つ
単純な問い合わせが大半を占める 小型モデルとモデルカスケード 定型は安いモデルで受け、難しいものだけ大型モデルへ回す

覚えておく数字と制限

  • InvokeModel の modelId に何を渡すかは呼び出し方で変わる。基盤モデルはモデル ID か ARN、推論プロファイルは ID か ARN、プロビジョンドモデルは Provisioned Throughput の ARN、インポートしたモデルはインポートモデルの ARN。
  • バッチ推論はプロビジョンドモデルに対応していない。 容量を買っている状態でバッチを流そうとしても使えない。
  • バッチ推論は tool calling（function calling）と structured output（response_format）にも対応していない。入力ファイルの各行は独立して処理され、多段のやり取りができないため。
  • ファインチューニング済みモデル（Amazon Nova 以外）は Provisioned Throughput を購入して Provisioned Model ARN を作る必要がある。元のモデル ARN を渡すと ValidationException になる。
  • 購入したプロビジョンドモデルは InService になってから呼び出す。状態は GetProvisionedModelThroughput で確認できる。

紛らわしいものの対比

試験では「予測可能な定常負荷」「スロットリングを避けたい」がプロビジョンドの合図で、「変動が大きい」「試験的に始める」がオンデマンドの合図になります。両方が必要なときは、平常時をプロビジョンドで支え、あふれた分をクロスリージョン推論のオンデマンドへ逃がす構成が定番です。
