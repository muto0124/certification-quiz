2.3 エンタープライズ統合アーキテクチャ

既存の社内システムに GenAI を差し込む話です。鍵は、誰が何を見てよいかを自前で作り直さず、既存の ID 基盤とアクセス制御に委ねることです。

会社に新しい部署を置くのに似ています。入館証は既存のものを流用し、稟議は既存のルートに乗せ、連絡は社内便を使う。全部を新設すると、部署は動いても会社が回らなくなります。

どこで間違えるのか

権限を GenAI 側で作り直す。 部門ごとに見える文書を変えたいとき、アプリの中に独自のアクセス制御を書きたくなります。しかし正解は、IAM Identity Center のグループとデータソース側のアクセス制御に委ねることです。二重管理はいずれ食い違います。

IAM のアクション名を API 名から推測する。 非同期の動画生成を始める API は StartAsyncInvoke ですが、同名の IAM アクションはありません。必要なのはモデル呼び出しの権限です。API 名とアクション名が一致するとは限りません。

環境ごとにコードやパイプラインを増やす。 開発と本番で違うモデルを試したいだけなら、アプリケーションは1本のまま、モデル ID を環境別の設定として外に出せば済みます。分岐を構造に持ち込むと、以後ずっと二重に保守することになります。

こう言われたら、これを選ぶ

問題文の手がかり選ぶもの理由
部門ごとに見える範囲が違う Identity Center のグループ 既存の ID 基盤に委ねる
外部 ISV に一部だけ渡す Q Business の data accessor 範囲を顧客側で決める
環境ごとに違うモデルを試す CDK と設定の外部化 パイプラインは1本で済む
昇格に自動テストと切り戻し CodePipeline と CodeBuild canary で戻せる
ジョブ状態を知りたい EventBridge の状態イベント ポーリングを減らせる
フローの実行権限を絞る Flow の service role 実行主体はロール側
エージェントの認証を既存 IdP に AgentCore Identity 入口と出口をまとめる

覚えておく数字と制限

  • API 名と IAM アクション名は別物。 StartAsyncInvoke で非同期ジョブを始める場合でも、IAM で要るのは bedrock:InvokeModel。同名のアクションを探しても見つからない。
  • Prompt Flows の実行主体は Flow に紐づけた service role。 開発者個人の IAM 権限では、Lambda ノードやナレッジベースノードが参照するリソースにアクセスできない。ロール側へ最小権限を付ける。
  • Amazon Q Business は IAM Identity Center と連携し、データソース側のアクセス制御に従って回答を絞る。外部 ISV へ渡す範囲は data accessor で顧客が決める。
  • Bedrock のバッチ推論ジョブは、開始・完了・失敗・停止といった状態変化を EventBridge のイベントとして受け取れる。GetModelInvocationJob のポーリングだけに頼らない。

紛らわしいものの対比

試験では「開発者には権限があるのに実行時に失敗する」という筋書きが出ます。答えはたいてい、実行主体であるサービスロールに権限が足りていない、です。同じ考え方が Knowledge Base の取り込みロールやエージェントのロールにも当てはまります。
