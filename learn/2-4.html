2.4 基盤モデル API の統合

呼び方の設計です。生成の途中から返すか、失敗にどう耐えるか、どのモデルへ流すか。この3つで構成が決まります。

電話の取り次ぎに似ています。相手を待たせないよう相槌を打ち（逐次）、話し中なら間を置いて掛け直し、何度も繋がらなければ一旦やめる（耐障害）。用件によって担当部署に回す（振り分け）。

どこで間違えるのか

完成を待ってから返す。 生成に 15 秒から 45 秒かかる処理を、出来上がるまで黙って待たせると、利用者は止まったと感じます。長い生成ほど、途中から見せる価値が大きくなります。

失敗したら即座に再試行する。 ピーク時に全クライアントが一斉に再送すると、混雑をさらに悪化させます。待ち時間を指数的に伸ばし、ばらつきを持たせ、繰り返す失敗は遮断します。

用途の違う API を選ぶ。 ナレッジベースを使わない普通の会話に検索付きの API を持ち出したり、逆に引用が要る場面で素の生成 API を選んだりすると、余計な組み立てが増えます。

こう言われたら、これを選ぶ

問題文の手がかり選ぶもの理由
生成中から表示したい ストリーミング API 部分応答を送れる
引用付きで逐次表示 RetrieveAndGenerateStream 検索と生成を一度に
検索を使わない通常会話 ConverseStream 共通の messages 形式
文書を添付して会話 ContentBlock の document text と一緒に渡せる
ピーク時の再試行 ジッター付き指数バックオフ 障害を広げない
繰り返す失敗を止める サーキットブレーカー 落ちた先を切り離す
難易度で自動的に使い分け Prompt Router 同一系列内で自動判定
能力の違うタスクを分ける アプリ側で明示的に分岐 系列を跨ぐため

覚えておく数字と制限

  • Intelligent Prompt Routing は同一モデルファミリー内での振り分け。 自分で構成する場合も、同じファミリーから2つ選び、応答品質の差を routing criteria として設定する。基準を満たさない場合は fallback model へ回る。
  • ファミリーを跨ぐ振り分け（たとえば SageMaker のエンドポイントと Bedrock の基盤モデル）は Prompt Router では扱えない。アプリケーションや Step Functions で明示的に分岐する。
  • ルーターを挟むことによる追加のオーバーヘッドは P90 で約 85 ミリ秒。安いモデルへ回る分と差し引きで、全体では下がることが多い。
  • Converse と ConverseStream は複数のモデルを同じ messages 形式で扱える。IAM ロールで認証すれば、実行環境や言語が違っても同じインターフェースで呼べる。
  • 再試行の設計は3点セット。指数バックオフ、ジッター、そしてサーキットブレーカー。ストリームを張り直す場合は重複を避けるための識別子も要る。

紛らわしいものの対比

問題文が「単純な質問は安いモデル、複雑なものだけ高性能モデル」と言っていれば Prompt Router です。「コードレビューと画像解析と翻訳」のように能力の系統が違うものが並んでいたら、明示的な分岐を選びます。
