2.5 アプリ統合パターンと開発ツール

GenAI を業務システムのどこに差し込むかを扱います。判断の軸はひとつ、その場で返せる処理か、受け付けて後で返す処理か。この線引きを誤るとタイムアウトします。

役所の窓口と同じです。住民票の写しはその場で渡せますが、審査が要る申請は受付番号を渡して後日連絡になります。どちらも窓口で待たせようとすると、行列が止まります。

どこで間違えるのか

長時間処理を同期リクエストに載せてしまう。 200 ページの契約書を読み、モデルに要約させ、外部システムに問い合わせ、人の確認まで待つ。これを API Gateway の一往復で終わらせようとすると、タイムアウトし、クライアントの再送で重複処理まで起きます。

ジョブの完了をポーリングで待つ。 状態を何度も問い合わせると、管理用のトラフィックが増えるうえ、気づくのも遅れます。ジョブの状態変化はイベントとして受け取れます。

ストリーミングを HTTP API でやろうとする。 軽くて安いほうを選びたくなりますが、API Gateway の response streaming は REST API のみの対応です。機能の有無が先に効きます。

こう言われたら、これを選ぶ

問題文の手がかり選ぶもの理由
決まった入出力の軽い処理 Step Functions Express 実装の手数が少ない
長文処理と人手確認を含む SQS と Standard ワークフロー 受付と処理を切り離す
ジョブの完了を知りたい EventBridge の状態イベント ポーリングより軽い
逐次表示とトークン制御 REST API の response streaming HTTP API は非対応
社内標準をコード提案に反映 Q Developer のカスタマイズ 各案件を変えずに済む
画面をすぐ用意したい Amplify の UI コンポーネント 宣言的に組み立てられる
コードを書かずに流れを組む Bedrock Prompt Flows ノーコードで連鎖を作れる
多様な文書から構造化データ Bedrock Data Automation 抽出をマネージドに寄せる

覚えておく数字と制限

  • API Gateway の response streaming は REST API のみ対応（2025 年 11 月のリリース）。HTTP API では応答がバッファされ、真のストリーミングにならない。
  • Lambda response streaming を外へ出す経路は3つ。Lambda 関数 URL（InvokeMode を RESPONSE_STREAM に変更）、InvokeWithResponseStream API、API Gateway REST API のプロキシ統合。
  • API Gateway REST API の response streaming では、統合タイムアウトが最大 15 分まで延び、10 MB を超えるペイロードも扱える。
  • Bedrock Data Automation のジョブ状態は EventBridge のイベントとして受け取れる。ポーリングは要らない。
  • 入口を早く用意する手段は目的で分かれる。画面は Amplify の宣言的コンポーネント、API 先行の設計は OpenAPI 仕様、処理の流れをコードなしで組むなら Prompt Flows。

一般論では「軽くて安いから HTTP API」ですが、ストリーミングが要件に入った瞬間に REST API しか残りません。運用負荷の比較より、機能の対応可否を先に見ます。

紛らわしいものの対比

問題文に「人が確認する」「数分かかる」「大量のページ」が出たら Standard と非同期の組み合わせです。逆に「S3 から取って、モデルに渡して、S3 に戻す」だけなら Express で足ります。
