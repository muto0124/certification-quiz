3.2 データセキュリティとプライバシー制御

守る場所は3つあります。経路（外に出さない）、保管（誰が見られるか）、実行時（何を通すか）。道具はそれぞれ違います。

金庫のある建物を思い浮かべてください。外から見えない専用通路で出入りし、部屋ごとに鍵を分け、持ち出すときは中身を検める。どれか一つでは守れませんし、通路の話をしているときに部屋の鍵を持ち出しても噛み合いません。

どこで間違えるのか

保管と実行時を同じ道具で守ろうとする。 すでに S3 に溜まっているログの機微情報を調べるのと、いま流れているチャットの入出力を止めるのとでは、使うサービスが違います。前者は保管側の走査、後者は実行時のフィルターです。

バケットポリシーだけ直して暗号化キーを忘れる。 配信先の S3 が KMS で暗号化されている場合、バケット側の許可だけでは書き込めません。鍵の側にも許可が要ります。

VPC エンドポイントを用途で取り違える。 素の推論と、ナレッジベースを介した検索付き生成とでは、呼ぶサービスが違います。片方だけ用意すると、もう片方がインターネット経由になります。

こう言われたら、これを選ぶ

問題文の手がかり選ぶもの理由
保存済みデータの機微情報調査 Amazon Macie 保管側を走査する
実行時の入出力を守る 機密情報フィルター その場で遮る、伏せる
社内独自の識別子パターン カスタム正規表現 形式一致で検出する
列や行の単位で権限を分ける Lake Formation データ層で強制する
外へ出さずに接続する 用途別の VPC エンドポイント API ごとに別に要る
別アカウントの S3 を使う バケットと鍵の両方の許可 片方だけでは通らない
役割で見せる範囲を変える ロール別のガードレール適用 応答から伏せられる

覚えておく数字と制限

  • VPC エンドポイントは用途ごとに別。 Converse などの推論は bedrock-runtime、RetrieveAndGenerate は bedrock-agent-runtime。エージェントの作成や更新は bedrock-agent。S3 へは gateway エンドポイントを併せて用意する。
  • SSE-KMS で暗号化した S3 へログを配信するには、バケットポリシーに加えて KMS キーポリシーで kms:GenerateDataKey を許可する。 バケット側だけ直しても書き込めない。
  • 別アカウントの S3 をナレッジベースのデータソースにする場合、こちら側のサービスロールに権限を付けるだけでは足りない。相手側のバケットポリシーと KMS キーポリシーでも、そのロール ARN を明示的に許可する。
  • 機密情報フィルターの動作は BLOCK と ANONYMIZE。開発とテストでは伏せる設定にして挙動を見て、本番では遮断に切り替える、という運用ができる。
  • ガードレールはリージョンをまたがない。データレジデンシーの要件があるなら、各リージョンに同じ設定のコピーを置く。

紛らわしいものの対比

両方を求める問題もあります。その場合は保管側の走査と実行時のフィルターを組み合わせた選択肢が正解になり、片方だけのものは落ちます。問題文に「既存のログ」と「ライブのチャット」が並んでいたら、この形です。
