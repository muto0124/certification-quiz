3.3 AI ガバナンスとコンプライアンス

守らせる仕組みを、アプリの実装ではなく認可の層に置きます。実装に任せると、いつか誰かが忘れます。

工場の安全管理に似ています。ヘルメットを着けましょうと朝礼で言うのは実装任せです。着けていないと通れないゲートを置くのが認可の層です。事故が起きてから記録を見返しても、事故は起きたあとです。

どこで間違えるのか

ログで後追いすればよいと考える。 Guardrail を付けずに呼ばれた記録が残っても、その呼び出し自体はもう通っています。必須にしたいなら、条件を満たさない呼び出しを認可の段で拒否します。

モデルの制限をアプリのコードに書く。 開発者が SDK から直接呼べば素通りします。組織として止めるなら、アカウントを跨いで効く仕組みに置きます。

どこで推論されたかを推定する。 クロスリージョン推論では、呼び出したリージョンと実際に処理されたリージョンが分かれます。監査では推測ではなく記録を見ます。

こう言われたら、これを選ぶ

問題文の手がかり選ぶもの理由
承認済み Guardrail を必須に GuardrailIdentifier 条件キー 認可の層で止まる
禁止モデルを組織で止める Organizations の SCP アカウントを跨いで効く
アプリ別に経路とコストを統制 application inference profile 直接呼び出しを禁じる
生成物と元データを結ぶ Glue Data Catalog とタグ 出所をたどれる
実際の推論リージョンを知る CloudTrail の追加データ 推定せずに済む
モデルの説明責任を残す SageMaker モデルカード 承認判断を記録する
Guardrail を他アカウントと共有 実行権限とリソースポリシー 両側の許可が要る

覚えておく数字と制限

  • bedrock:GuardrailIdentifier 条件キーは Converse、ConverseStream、InvokeModel、InvokeModelWithResponseStream に効く。 Allow だけでなく StringNotEquals の明示的 Deny を併せて置くと、他にどんな権限があっても別の Guardrail では呼べなくなる。
  • SCP で禁止モデルを止めるときは bedrock:InvokeModel だけでなく bedrock:InvokeModelWithResponseStream と bedrock:CreateModelInvocationJob も対象にする。ストリーミングとバッチを外すと抜け道が残る。
  • クロスアカウントで Guardrail を共有するには、呼び出し側の bedrock:ApplyGuardrail 権限と、Guardrail 側のリソースベースポリシーの両方が要る。
  • クロスリージョン推論で実際に処理されたリージョンは、呼び出し元リージョンの CloudTrail イベントにある additionalEventData.inferenceRegion で確認する。

紛らわしいものの対比

問題文の「アプリケーションの実装に依存せず」「組織全体で」という言い回しが合図です。ログや監視を挙げている選択肢は、強制ではなく事後の確認なので落とせます。
