4.1 コスト最適化とリソース効率

払っているのはトークンです。減らす道は3つ。そもそも送らない、送ったものを使い回す、安いモデルに回す。

電気代の下げ方と同じです。使っていない部屋の明かりを消し、洗濯はまとめて回し、古い家電を省エネ型に替える。一つやれば劇的に下がるわけではなく、積み重ねで効いてきます。

どこで間違えるのか

文字数でトークンを見積もる。 実際に送られるのは、会話履歴も添付文書もツールの実行結果も含んだ構造です。しかも数え方はモデルごとに違います。文字数からの換算では上限にもコストにも届きません。

キャッシュの前に変わるものを置く。 プロンプトキャッシュは前方一致で効きます。先頭にタイムスタンプや会話要約を置くと、後ろがどれだけ同じでも毎回外れます。

完全一致のキャッシュで済ませる。 同じことを違う言い回しで聞く問い合わせは、文字列一致では拾えません。意味で当てる仕組みが要ります。

こう言われたら、これを選ぶ

問題文の手がかり選ぶもの理由
送信前にトークンを知りたい CountTokens API 課金と同じ数え方
同じ長い前置きを何度も送る プロンプトキャッシュ 前方一致で再利用する
言い回しの違う同じ質問 セマンティックキャッシュ 意味で当てる
ピークだけ超える クロスリージョン推論 固定費を増やさない
平常時の負荷が読める プロビジョンドスループット 安定分を賄う
アプリ別にコストを分ける application inference profile 利用を帰属できる
単純な質問が大半 小型モデルへの振り分け 高い方を使わずに済む

覚えておく数字と制限

  • CountTokens はモデル固有で、実際に課金されるのと同じカウントが返る。 InvokeModel と Converse の両方の入力形式を受け付けるので、送るつもりの構造をそのまま渡して事前に測れる。
  • プロンプトキャッシュは前方一致。長い契約書などの静的な部分を先頭に固定し、毎回変わる要素は後ろに置く。効いているかは CacheReadInputTokens と CacheWriteInputTokens で確認する。
  • セマンティックキャッシュでは、類似度のしきい値、TTL、テナントの境界を決める。近すぎるしきい値は誤った再利用を招く。
  • 平常時とピークの性質は違う。予測できるベース負荷はプロビジョンドスループットで支え、突発分はクロスリージョン推論のオンデマンドへ逃がす、という併用が定番。

「使わない時間帯の固定課金を避けたい」と書かれていたら、全量をプロビジョンドで確保する選択肢は落ちます。逆に「常時一定の負荷」だけならオンデマンド一本も割高になります。

紛らわしいものの対比

試験では「同じ資料を何度も送る」「40% が似た問い合わせ」といった記述が合図になります。前者はプロンプトキャッシュ、後者はセマンティックキャッシュで、狙う重複の種類が違います。
