4.3 監視・オブザーバビリティ

動いているかではなく、期待どおりかを見ます。GenAI では CPU やエラー率より、トークン・応答品質・推論経路のほうが効きます。

健康診断に似ています。体温だけ見ても分かることは限られます。血液検査で数値を取り（呼び出しログ）、問診で自覚症状を聞く（品質評価）。3つ揃って初めて、どこが悪いのかに近づけます。

どこで間違えるのか

インフラ監視で足りると思ってしまう。 CPU もエラー率も正常なのに、回答が事実と違う、という状況が普通に起きます。GenAI では応答の中身を見る層を別に用意しないと、劣化に気づけません。

平均値のダッシュボードで遅延を追う。 特定の顧客セッションだけが遅いとき、その 1 本は平均に埋もれます。サービス境界をまたいで 1 リクエストを追うには分散トレーシングが要ります。

有効化を忘れる。 モデル呼び出しログもエージェントのトレースも、既定では取られていません。「後から調べる」と言われた時点で、先に有効化しておく必要があります。

こう言われたら、これを選ぶ

問題文の手がかり選ぶもの理由
何を送り何が返ったか見たい モデル呼び出しログ 中身がログに残る
遅い 1 セッションを追う X-Ray の分散トレーシング 平均では見えない
エージェントの推論経路 InvokeAgent のトレース 標準機能で追える
トークン急増の原因を特定 呼び出しログと requestMetadata アプリ別に切り分けられる
いつもと違う動きを捕まえる CloudWatch 異常検出 しきい値を決めずに済む
キャッシュが効いているか キャッシュのトークン指標 体感でなく数字で見る
技術指標と業務指標を並べる 複合アラームと統合ダッシュボード 相関した劣化を捕まえる

覚えておく数字と制限

  • Bedrock のモデル呼び出しログは既定で無効。 有効にして CloudWatch Logs か S3 へ配信する。requestMetadata にアプリ名やリリース版を入れておくと、後からリクエスト単位で切り分けられる。
  • エージェントの推論経路は InvokeAgent で enableTrace=true を指定すると応答に含まれる。外形監視では代替できない。
  • AgentCore では閲覧側と送信側の両方が要る。 CloudWatch Transaction Search を有効にするだけでは見えず、ADOT などでエージェントのコードを計装して trace と span を出す必要がある。
  • プロンプトキャッシュが効いているかは CacheReadInputTokens と CacheWriteInputTokens で見る。読み取り側が伸びていれば再利用されている。
  • ナレッジベースの取り込みログは APPLICATION_LOGS。ジョブ全体だけでなく文書ごとの状態も記録される。

紛らわしいものの対比

問題文が「全体の傾向」「使用量の可視化」と言っていれば Logs Insights とメトリクス、「特定のセッション」「どこで時間を使っているか」と言っていれば X-Ray です。エージェントの内部まで追う話なら、さらにトレースの有効化が要ります。
