呼び出しと推論基盤 — リクエストがモデルに届くまで

同じモデルでも、どの API で呼び、どの経路を通し、容量をどう買うかで、応答の速さもコストも変わります。

上から下へ、クライアントのリクエストがモデルに届くまでの5段です。設定値を再デプロイなしで差し替えるなら AppConfig を実行の段に挟みます。

渡す文脈をつくるのは → 検索経路 モデルの前後の検査は → 安全と統制の関門 呼び出しの記録は → 観測と評価の配線

同じ段を争うもの

文字単位で返すならストリーミング対応の API を選びます。スパイクがあるならオンデマンド、量が読めるならプロビジョンド、即時性が不要ならバッチです。

どこを読むか

段候補深掘り
モデルの選定 Nova / 推論プロファイル / intelligent prompt routing 1.2
容量の買い方 オンデマンド / プロビジョンドスループット 2.2
呼び出し API Converse / ConverseStream / InvokeModel / InvokeModelWithResponseStream 2.4
コストの手当て プロンプトキャッシュ / バッチ推論 4.1
遅さの手当て ECS / AppConfig 4.2

このマップだけでは足りない場面: 遅さの原因が検索側にあるときは 検索経路、レイテンシーの内訳を測りたいときは 観測と評価の配線 を見てください。

このマップが束ねるタスクの問題

番号はこのマップが束ねる5タスクの問題です。図に出るサービスと一対一ではありません。クイズの出題範囲に番号を入力して解いてください。

問題データを読み込めませんでした。問題番号の一覧はオンラインで開き直すと表示されます。
